# 面试故事：三个真实 Bug 的完整排查链路

> 用途：AI 全栈实习面试中回答"讲一个你印象深刻的 Bug / 你如何解决线上问题"类问题。
> 三个案例全部真实发生在本项目（智慧养老安全用药辅助平台），每个都有可复现的验证手段，不是编的。
> 每个故事给三个版本：**30 秒电梯版**（面试官随口问）、**3 分钟完整版**（让你详细讲）、**追问预案**。

---

## 故事一：冲突引擎"成分匹配"静默失效 —— 最危险的不是报错，是不报错

### 30 秒版
"我给用药冲突引擎新增规则时，发现基于药物成分的规则永远不触发。排查发现引擎把成分字符串直接当列表迭代——Python 里迭代字符串得到的是单个字符，'左旋多巴、苄丝肼'被拆成了{'左','旋','多','巴'…}。这个 Bug 存在很久没暴露，因为老规则恰好都能靠药名子串匹配兜底。修复后我补了成分级规则的回归用例。"

### 3 分钟版
1. **现象**：知识库从 106 种药扩到 144 种，同时新增 38 条冲突规则。测试"左旋多巴 × 甲氧氯普胺"（帕金森病人禁用胃复安，经典禁忌）时，规则死活不触发；但同批的单药老年慎用规则（PIM 类）能触发。
2. **定位**：两类规则走不同匹配路径——PIM 单药规则用药名**子串**匹配（"喹硫平" in "富马酸喹硫平片" ✓），双药规则用**成分归一化精确**匹配。我在本地直接 import 引擎模块，dump 中间变量：`_med_terms()` 返回的词表是 `{'丝','多','、','巴','左','苄','多巴丝肼片',…}` ——成分被拆成了单字符。
3. **根因**：`for ing in med.get("ingredients") or []` 假设 ingredients 是 list，但后端传来的是字符串 `"左旋多巴、苄丝肼"`。Python 迭代 str 就是逐字符迭代，没有任何报错。
4. **为什么潜伏这么久**：老的 108 条规则涉及的药，药名本身都含成分词（如"阿司匹林肠溶片"含"阿司匹林"），子串兜底路径一直能命中——成分归一化路径从未真正工作过，也没有测试能区分这两条路径。
5. **修复**：字符串按 `、，;；` 切分成列表，同时保留对 list 的兼容（一行 isinstance 判断）。顺带排查了全项目所有 `ingredients` 的使用点，RAG 建库脚本里有同样的隐患，一并修了。
6. **验证**：修复后 dump 词表 `{多巴丝肼片, 左旋多巴, 苄丝肼, 抗帕金森病药}` ✓；4 条依赖成分匹配的新规则全部触发；36 项主流程 e2e + 14 项家庭协同 e2e 全绿。

### 追问预案
- **Q: 为什么测试没发现？** A: 之前的用例恰好都走药名子串路径。教训是测试要覆盖"匹配机制"本身而不只是"业务结果"——我后来专门加了只用成分名（不带药名）的冲突用例。
- **Q: 怎么快速定位的？** A: 不猜，直接本地 import 引擎模块复现调用，print 中间数据结构。看到单字符集合的一瞬间根因就明确了。
- **Q: Python 还有什么类似的坑？** A: `dict.update(str)`、`list(str)`、`set(str)` 都会静默拆字符；`for x in obj` 对 str/bytes 和 list 行为完全不同但都不报错。防御手段是关键入口做 isinstance 校验或用类型标注。

## 故事二：FAISS 缓存陈旧 —— 注释会骗人，指标不会

### 30 秒版
"RAG 问答一直'能用'，但我核对指标发现向量索引只有 490 条，语料实际有 756 个片段——266 个片段永远检索不到。根因是持久化缓存从不校验语料是否变化，代码注释却写着'语料变化则重建'。我加了语料指纹（条数+内容SHA256）校验，不一致自动重建，现在检索覆盖 1022/1022，缓存命中时启动还从 47.6 秒降到 19.7 秒。"

### 3 分钟版
1. **现象**：没有任何报错，问答也出结果。是我在做知识库扩容时例行核对启动日志：`文档向量缓存完成: 490 x 512`，但当时语料构建日志是 `756 片段`——两个数字对不上。
2. **定位**：读缓存加载代码发现 `_load_store` 只判断缓存文件是否存在，存在就直接反序列化使用；上面一行注释写着"语料变化则重建"，但**没有任何实现**。语料在某次扩容后变了，缓存还是旧的。
3. **影响分析**：混合检索里 BM25 一路是全量语料，FAISS 一路缺了 35% 的片段——语义检索的召回被静默砍掉一块，表现为"有些明明库里有依据的问题，引用质量不稳定"。
4. **修复**：持久化时写入 meta.json 语料指纹（片段数 + 全量内容 SHA256 前 32 位）；加载时指纹不一致就返回 False 走重建。删除旧缓存强制重建一次，之后重启自动命中缓存。
5. **修复过程中还揪出一个连带 Bug**：全新构建路径直接 500——`TypeError: '_QueryPrefixEmbeddings' object is not callable`。原因是自定义的 embedding 包装类没继承 langchain 的 Embeddings 基类，新版 langchain_community 对非 Embeddings 实例走 callable 兼容路径直接调用对象。之前一直走"缓存加载"路径（传的是绑定方法，恰好可调用）所以没暴露。给包装类补了 `__call__` 转发 `embed_query` 修复。
6. **验证**：重建日志 `1022 x 512 (填充 1022/1022)`；再次重启日志显示"FAISS 索引从缓存加载"、启动 19.7s；`/qa` 响应新增 `corpusChunks` 字段，前端引用面板直接展示知识库规模，指标对用户可见。

### 追问预案
- **Q: 为什么不用文件修改时间做校验？** A: mtime 不可靠（拷贝、git checkout 都会变），内容指纹才是语义上的"语料是否变了"。代价是启动时算一次 SHA256，千级片段毫秒级，可接受。
- **Q: 这给你什么方法论？** A: ①"看起来能跑"≠正确，要有可核对的守恒量（向量数==文档数这种）；②注释描述的行为必须有对应实现和测试，否则就是谎言；③缓存必须带失效判据，这是缓存设计的第一课。
- **Q: RRF 融合为什么能掩盖这个问题这么久？** A: BM25 路召回正常时，融合结果看起来还行——多路召回提高了鲁棒性，也掩盖了单路退化。所以每一路都要有独立的健康指标。

## 故事三：分布式冷启动时序 —— 用 id 做字典键，而所有 id 都是 None

### 30 秒版
"AI 服务比后端先启动时，识药 Top1 从'阿司匹林'(0.875) 错配成'阿米替林'(0.5)。根因是双重的：词典拉取失败回退到种子文件，种子数据没有数据库 id 全是 None；而候选匹配结果用 `scored[item['id']]` 做字典键，106 条全部写到同一个 None 键上互相覆盖，只剩最后一条。我改用枚举索引做键，并把重试窗口从 30 秒扩到 2 分钟容忍后端慢启动。"

### 3 分钟版
1. **现象**：隔夜后全部服务停机，按 MySQL → 后端 → AI 顺序重启。回归测试识药用例失败：同一张阿司匹林药盒图，Top1 变成"盐酸阿米替林片"，置信度 0.5，正好卡在低置信阈值上。
2. **定位**：先看 AI 启动日志——`药品词典已更新` 的来源不是后端接口而是种子文件兜底（后端当时还没就绪，30 秒重试窗口耗尽）。再对比两条路径的数据结构：后端返回带数据库 `id`，种子文件构造的条目 `id` 全是 `None`。
3. **根因**：`match_candidates` 里 `scored[item["id"]] = {...}` 用 id 做键。种子路径下 106 条药全部命中 `scored[None]`，互相覆盖只剩字典里最后一条（恰好是阿米替林）。**Top1 不是匹配错了，是候选池里只剩一个候选。**
4. **为什么线上路径没炸**：正常时序下 AI 从后端拉到词典，id 各不相同，键不冲突。这个 Bug 只在"AI 先于后端启动 + 走种子兜底"时触发——典型的冷启动时序缺陷。
5. **修复**：①键改用 `enumerate` 的索引，语义上就是"第 i 条候选"，与 id 无关；②重试窗口 6×5s → 24×5s（约 2 分钟），覆盖后端冷启动（Spring Boot + DbBootstrap 种子导入）慢于 AI 的场景；③保留种子兜底本身——它是弱依赖降级设计，方向没错，错在实现假设了 id 唯一。
6. **验证**：修复后 AI 直连 Top1=阿司匹林肠溶片 conf=0.875、候选 3 条、lowConfidence=False；后端代理路径 medicationId 正确回填；模拟"AI 先启动"再测一次通过；36 项 e2e 全绿。

### 追问预案
- **Q: 为什么不一开始就用索引做键？** A: 原实现假设"id 一定存在且唯一"，这个假设在后端路径成立、在兜底路径不成立。教训：**降级路径的数据契约和主路径不同，必须单独测试降级路径**，我现在的回归里专门有"AI 先于后端启动"的用例。
- **Q: 服务间依赖还怎么处理？** A: 本项目 AI 与后端是互相弱依赖：AI 启动拉不到就重试+种子兜底；后端启动时向 AI 推规则，推不到也不失败（AI 会自己来拉）。两边都能独立自愈，启动顺序不敏感——这也是我后来给 DbBootstrap 加"幂等增量同步"的原因，任何顺序重启最终状态一致。
- **Q: 置信度 0.5 为什么可疑？** A: 我们的打分公式是 `min(0.99, 0.75 + len/40)`（精确子串）或编辑距离分（≥0.45 才入围），0.5 是编辑距离路径的低分——Top1 走模糊匹配而不是精确匹配，本身就说明候选池不对劲。熟悉自己系统的数值分布，异常一眼可见。

## 通用讲法建议

1. **永远按"现象 → 定位过程 → 根因 → 修复 → 验证 → 教训"讲**，重点放在"定位过程"——面试官考察的是排查思路，不是 bug 本身。
2. **主动讲"为什么之前没发现"**，这展示你对测试盲区的理解，比修复本身更加分。
3. **每个故事准备一个可核对的数字**（490 vs 756、conf 0.875、106 条覆盖成 1 条），数字让故事可信。
4. 三个故事分别对应三类经典问题：**语言特性坑**（str 迭代）、**缓存一致性**（失效判据）、**分布式时序**（启动顺序与数据契约），面试官从哪个角度追问都接得住。
5. 如果面试官问"还有什么印象深刻的"，可加讲：SSE 推送测试因产品去重设计（同组合 1 小时窗口）出现小时级假失败——测试用例本身也要审查对业务规则的隐含假设。
